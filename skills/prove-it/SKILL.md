# Prove it

Make the claim testable, check the actual result, and report only what the
evidence supports. Apply while planning a change and before declaring it
complete. Scale the proof to the behavior and risk.

## Define the claim

Translate the request into observable acceptance conditions. Name the input,
action, expected result, relevant failure case, and state or environment.
Use expectations from the request or an independent contract, not values
calculated by the implementation being checked.

Choose the smallest check that can detect the credible failure. Existing
tests, a command with a fixture, an API call, a browser flow, or inspection
of a generated artifact may suffice. Compilation proves a type/build claim;
it does not establish that a user flow or data change works.

## Exercise the real boundary

For a bug, demonstrate the original failure before the fix when feasible,
then run the same scenario after it. For new behavior, check both the requested
outcome and a failure or boundary case that could invalidate it. For a
behavior-preserving refactor, compare representative outputs and side effects.

Reach the production behavior at its owning boundary. If a feature crosses
UI, API, and storage, trace those boundaries far enough to verify the claim,
including persisted state when persistence matters. Mocks may isolate an
unavailable external service; they cannot prove the integration they replace.

Check that the observation could detect failure. A constant response,
self-comparison, stale screenshot, or expected result generated by the same
algorithm gives no independent proof. Use a negative control or a focused
mutation when useful and safe, restoring it before the final check.

For timing or concurrency claims, record the workload, baseline, repetitions,
and variability. Do not infer a speedup from one noisy run or correctness
from one successful race. Protect shared data and live environments; use
isolated fixtures for destructive scenarios.

## Keep and report the evidence

Run required repository checks and the focused acceptance checks. Verify
the final state after the last relevant edit or integration. Record enough
to rerun them: command or steps, inputs, environment, result, and commit or
working-tree state when it matters.

Add a durable regression test when it guards a meaningful recurring failure.
Avoid permanent tests that mirror wording or implementation, and avoid
building a verification framework for a small reversible change.

Report what passed, failed, or could not be checked and why. Distinguish
behavioral proof, static evidence, and inference. A missing environment is
a verification gap, not success. A subagent's claim needs inspectable output
or a rerun; agreement alone proves nothing. Never say the feature works
because the worker said so or unrelated checks passed.
